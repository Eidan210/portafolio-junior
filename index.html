Cómo trabajo

Principios de trabajo aplicados, no definiciones de manual: la forma concreta en la que abordo un problema y lo dejo entregado.

  • Diagnóstico antes que parche

    No toco una línea hasta reproducir el fallo. Aíslo la causa real, corrijo el origen —no el síntoma— y compruebo que el caso que rompía ahora pasa. Un ya funciona sin verificar no cuenta como resuelto.

    1. 01 Reproducir el fallo Si no consigo repetirlo, no sé qué estoy arreglando.
    2. 02 Aislar la causa Logs, el caso mínimo que rompe y descartar lo que no interviene.
    3. 03 Corregir el origen Si el arreglo necesita una excepción encima, el diagnóstico falló.
    4. 04 Verificar el caso que fallaba Y revisar que no he roto lo que ya funcionaba alrededor.

  • Entrego sostenido, no a ráfagas

    Avanzo en incrementos pequeños y publicables. Commits atómicos con mensaje descriptivo antes que un volcado de cambios al final.

  • Escribo el porqué

    README que explica la decisión tomada, no solo cómo se instala. Comentarios donde el código no se explica solo.

    • Conventional Commits
    • Historial legible

  • Reviso lo que ya funciona

    Una versión que funciona no es el final: vuelvo sobre ella para modularizarla y quitarle deuda. Menos duplicación y cada módulo con una sola responsabilidad.

    v1.0 → v2.0 modular

  • Documentación oficial primero

    Cuando me atasco sigo siempre el mismo orden de fuentes: el tutorial enseña una solución, la documentación explica por qué es esa.

    • Documentación oficial Primera fuente
    • Código fuente e issues Apoyo
    • Tutorial de terceros Último recurso

  • Nativo antes que dependencia

    Antes de instalar algo mido lo que cuesta mantenerlo. Este portafolio corre sin build ni librerías: HTML, CSS y JavaScript puro. Cero dependencias es también cero avisos de seguridad que perseguir y una carga inicial mínima.

    • Evaluar alternativas
    • Medir el coste real
    • Elegir lo mantenible
